# Stage 2.2 — Narrow Audit: Provider & Feature Coupling

## Focus
- Whether feature hooks and contexts are decoupled from the shared provider shell
- Whether feature state is owned locally or by the global shell
- How persistence and session behavior are shared across feature modules

## Findings

### 1. Feature state is mostly local and composable
- Cart and favorites state are encapsulated in feature-specific hooks: useCart and useFavorites.
- These hooks own their local update logic and expose a narrow API to the provider layer.
- This is a good separation of concerns and makes the feature logic easier to reason about.

### 2. The provider layer is still a central integration point
- CartProvider and FavoritesProvider simply wrap those feature hooks and expose them through context.
- The global provider shell in src/context/AppProviders.js imports these feature providers directly, which creates a clear but somewhat strong coupling between shared infrastructure and business feature modules.

### 3. Shared persistence is abstracted through a hook, but it is still fairly generic
- useSessionState is a reusable persistence hook and helps avoid feature-specific storage logic.
- However, it is still a very broad abstraction and is used by multiple features without a stronger contract for schema, versioning, or data ownership.
- This is fine for a small app, but it can become a source of implicit coupling over time.

### 4. Favorites logic is more coupled to auth than cart logic
- useFavorites directly depends on AuthContext and repository calls for persistence.
- That makes it more tightly coupled to authentication and backend concerns than the cart flow.
- It is still understandable, but the boundary could be cleaner if the auth-dependent persistence concerns were isolated further.

## Architectural Takeaway
The feature layer is reasonably modular, but the shared provider shell is still a point of integration that reaches into feature modules. The main risk is not poor design today, but growing coupling as more feature providers are introduced.

## What the next pass should target
- The data/service boundary: whether repositories, view models, sync layers, and domain contracts remain coherent and separated.
