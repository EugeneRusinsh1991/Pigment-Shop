# Stage 2.4 — Narrow Audit: Provider/Feature Coupling & Service/Data Boundaries

## Focus
- Whether feature modules are coupled to repositories and shared services in a clean way
- Whether the data layer is isolated from UI and feature concerns
- Whether the Firebase adapter is a stable boundary or a source of implicit coupling

## Findings

### 1. Repositories are relatively clean adapters
- The favorites repository and auth repository are thin adapters over Firebase APIs.
- They expose narrow, explicit operations and keep the persistence details in one place.
- This is a good architectural pattern because it localizes backend coupling.

### 2. Feature hooks still reach into repositories directly
- useFavorites imports favoritesRepository directly and wires it to auth state and UI state updates.
- That means the feature logic is still coupled to a concrete persistence implementation, even though the repository is a relatively thin boundary.
- This is acceptable for a small app, but it is less ideal than using a more domain-oriented service boundary.

### 3. The Firebase module is a strong infrastructural boundary, but it is still globally coupled
- src/services/firebase/index.js centralizes Firebase initialization and exports auth/db.
- This is a clear infrastructure boundary, but many modules import from it directly, which means the rest of the app is still coupled to Firebase-specific contracts.
- The architecture would be stronger if more of the app interacted with a higher-level domain service layer instead of Firebase primitives.

### 4. The data layer is better separated than the feature layer, but not fully abstracted
- Catalog sync and catalog state are reasonably separated from the UI layer.
- However, the app still has several direct repository/service imports from feature hooks and contexts, which means the data boundary is only partially insulated.

## Architectural Takeaway
The project shows a solid foundation for service/data boundaries: repositories are centralized and the Firebase adapter is isolated. The main issue is that the app still leaks concrete persistence and infrastructure dependencies into feature-level logic more often than ideal.

## Suggested Direction
- Introduce a slightly higher-level feature service layer for favorites/auth/cart interactions so feature hooks depend on domain services rather than raw repositories or Firebase modules.
- Keep the current repository layer as a low-level adapter, but make the higher-level service layer the main boundary for features.
